# 2026-10-23 frpc-android 项目启动

## 任务
实现 frpc 安卓客户端，参考 luckjiawei/frpc-desktop 的界面功能；要求：安装包小、运行快、跨平台。

## 关键决策
- 技术栈：Kotlin Multiplatform（shared: android+jvm 双端逻辑层）+ Jetpack Compose M3（原生、包体小、启动快）
- frpc 引擎：frp v0.71.1 源码 Go 交叉编译（arm64 静态 + x86_64 NDK cgo），assets 分发、按 ABI 安装到 filesDir/bin
- 版本矩阵（重要）：AGP 8.13.2 + Gradle 8.13 + Kotlin 2.4.21 + compose-bom 2026.06.00（compose 1.11.3）。
  踩坑记录：① AGP 9.x 内置 Kotlin 2.2.10 且禁显式 kotlin.android 插件、KMP 组合方式大改 → 弃用；
  ② compose-bom 2026.09（compose 1.12）要求 compileSdk 37，AGP 8.13.2 最高 36 → 降 BOM；
  ③ KMP 的 androidLibrary{} 新 DSL 仅 AGP9 支持，AGP8 用 androidTarget() + 独立 android{} 块；
  ④ kotlin{compilerOptions{}} 顶层是 KotlinCommonCompilerOptions 无 jvmTarget → android 目标靠 AGP compileOptions 同步，JVM 目标用默认。
- ktoml 0.7.1 缺陷：[[proxies]] 内点分键（transport.x=y）每个键生成一个同名子表导致解码丢失
  → FrpcToml.decode 解析后 mergeDuplicateTables 合并同名子表修复（有真实 frpc 示例解析测试覆盖）
- 导航不用 Navigation-Compose（减依赖），自写 AppNavigator 返回栈；编辑草稿放 Activity 级 ConfigEditorStore 防旋转丢失
- 持久化：JSON 文件（configs.json 原子写）+ SharedPreferences，不引 Room/KSP

## OpenWRT frps 升级到 0.71.1 + 全协议重测（v1.0.4）
- 升级方式：Go 源码编译 frps 0.71.1 linux/amd64 静态二进制 → SSH 原始字节流上传（路由器无 base64/sftp）→ sha256 校验 → 路由器上先跑 --version 验证 musl 兼容 → 备份后切换
- 备份：/usr/bin/frps.0.51.3.bak、/etc/config/frps.bak-20261023（回滚：cp 回去 + /etc/init.d/frps restart）
- UCI 新增端口（init 脚本会把任意 UCI option 透传进 frps.ini）：kcp_bind_port=7000、quic_bind_port=7003、vhost_http_port=7004、vhost_https_port=7005、tcpmux_httpconnect_port=7006
- 期间发生一次神秘 flash 回滚（22:51 左右，二进制/配置/备份全回到 0.51.3 状态，但 uptime 连续、dmesg 无事件）→ 重做后 2 分钟监控稳定；教训：改动后必须监控确认
- 重测结果 10/11 通过：tcp+TLS/tcp/websocket/kcp/quic/stcp+visitor/sudp+visitor/http/https/tcpmux 全部数据回环成功
- **最重要的真因发现**：frpc 的 kcp/quic 不会改写端口，始终拨 serverAddr:serverPort → 服务端 kcp_bind_port/quic_bind_port 必须与客户端 serverPort 一致（之前的 KCP 失败正是 7002 vs 7000 不匹配！）
- https 代理 = TLS 透传（本地服务必须自己是 HTTPS），frps 只按 SNI 路由，不需要自身证书
- wss 在 frps 自身 TLS 下不可用（源码确认：TLS 解包后走 yamux，与 websocket 升级不兼容）→ 实际用法是 frps 前置 nginx/CDN 做 TLS 终止
- 顺带发现：用户路由器 WAN 在 22:33 起不通（eth1 DOWN，非本次改动导致，需用户自查光猫/宽带）
